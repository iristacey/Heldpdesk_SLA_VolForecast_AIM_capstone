## 1. Problem Statement 

| Element | Definition |
|---|---|
| Core retrospective task | Analyze completed Ticket records and compare elapsed creation-to-resolution time to project-configured priority references. |
| Core predictive task | Forecast counts of exact `Ticket` type created per UTC calendar day, with separate 7- and 30-day horizons. |
| SLA target | Project reference attainment; unknown priority is excluded. |
| Forecast target | Daily Ticket count; inputs are only past counts and calendar features. |
| Machine learning task | Univariate time-series regression via model comparison: same-weekday-last-week seasonal-naive baseline, weekly ETS (statistical), XGBoost autoregression on 28-day lags, and a mutual-information/PCA-selected Ridge regressor. Each candidate is backtested on expanding-window origins and selected per horizon by validation MAE — this is supervised regression, not classification. |
| Primary metrics | SLA reference-met counts/rates by mapped priority; forecast validation/test MAE and RMSE. |
| Supporting metrics | WAPE, sMAPE, signed bias, empirical interval coverage, data-quality/coverage counts. |
| Alert event | None. This is not an individual live-ticket breach warning system. |

**In summary:** we did two things with historical help desk tickets. First, we checked how many past tickets were resolved within their priority's target time. Second, we tried to predict how many new tickets will show up each day over the next week and next month, using only past ticket counts and the calendar (day of week, time of year); no live monitoring or per ticket alerts are involved.

**Research acceptance criterion:** after validation-only selection, require held-out MAE below the same-weekday seasonal baseline at both horizons, reporting RMSE, bias and coverage. The corrected historical run meets this criterion: 5.05 versus 6.41 tickets/day at 7 days and 4.67 versus 6.49 at 30 days. This is not owner-approved operational acceptance or business success.

**Proposed business success criterion (not measured or owner-approved):** a human-reviewed pilot should reduce overtime hours per 100 tickets by **at least 10%** versus a matched baseline without worsening an owner-approved service-attainment rate. This requires approved ticket/overtime/service-clock definitions, costs, matching rules, pilot period and stop conditions, plus current representative data. The retrospective reference rate is not that approved KPI.

### 2.1 Data structure

The raw source is one flat table, 66,691 rows by 58 columns, grouped by role:

| Group | Example columns | Role |
|---|---|---|
| Identity/keys | `id`, `issue_num`, `issue_proj` | Unique record and (masked) project/issue references. |
| Actors | `issue_reporter`, `issue_assignee`, `issue_contr_count` | Masked user identifiers; `issue_assignee` is 46.55% missing. |
| Classification | `issue_type`, `issue_priority`, `issue_status`, `issue_resolution` | Ticket type, priority, workflow status, resolution outcome; the primary cohort filters `issue_type == Ticket` and `issue_resolution == Done`. |
| Timestamps | `started`, `ended`, `issue_created`, `issue_resolution_date`, `last_change_date` | Parsed as UTC; `issue_created` drives the daily forecast series and `issue_resolution_date` drives the SLA reference duration. |
| Workflow-state durations | 16 `wf_*` fields | Elapsed seconds in each named workflow state; mostly sparse, kept only as diagnostics. |
| Workflow-state transition counts | 16 `wfe_*` fields | Count of times an issue passed through each state; always populated. |
| Process summary | `wf_total_time`, `processing_steps`, `issue_comments_count` | Total workflow processing time and step/comment counts; diagnostic only. |

The complete generated reference for all 58 columns is `output/issue_helpdesk/data_dictionary.csv`.

The **engineered structure used for forecasting** is a separate, narrower table, one row per calendar day (2,628 rows), built only from `issue_created` day counts:

| Feature group | Columns | Notes |
|---|---|---|
| Target | `ticket_count` | Scoped Ticket records created that UTC day; 0 for the 344 zero-ticket days. |
| Lag features | `lag_1` to `lag_28` | Prior 28 days' counts, computed only from history strictly before the target date. |
| Rolling means | `mean_7`, `mean_28` | 7- and 28-day trailing averages, same past-only rule. |
| Calendar encodings | `weekday_sin`, `weekday_cos`, `year_sin`, `year_cos` | Cyclical day-of-week/day-of-year encodings for weekly and annual seasonality. |

**In summary:** the raw file is wide (58 columns covering who touched a ticket, when, and how long it sat in each workflow state), but the forecasting model only ever sees a narrow, purpose-built table of one row per day: how many tickets showed up, how many showed up on recent days before it, and where that day falls in the week and year. Keeping these two structures separate is what prevents the model from accidentally peeking at same-day information it would not have in advance.

## 4. From issue events to daily volume

1. Parse `issue_created` with mixed fractional-second formats as UTC.
2. Restrict the forecast target to `issue_type == Ticket` and the documented 2016+ scope.
3. Aggregate to one count per calendar day.
4. Fill dates without rows as zero only under the explicit completeness assumption.
5. Create past-only lag, rolling-mean, weekday and annual-cycle features.

The result is **2,628 calendar daily observations**, averaging **10.4 tickets/day**, with 344 assumed zero-arrival days. Counts range from zero to 88. Gaps in event dates are not interpolated as minute-level readings.

**In summary:** we turned a list of individual tickets into a simple daily count, meaning how many tickets came in on this day, then added helper signals like how many came in over the last 4 weeks and whether it is a Monday or a December so the model can spot patterns.

## 5. Forecast experiment

The project compares 7- and 30-day horizons. Both use weekly-spaced expanding-window origins, a 365-day validation period for model selection, and a later 365-day test period kept separate. The 7-day experiment yields 52 validation origins and 51 final-test origins; the 30-day experiment yields 48 origins in each split because each forecast must fit entirely inside its evaluation window. The 30-day output is a daily path for the next 30 days, not one monthly total. Its weekly origins overlap, so pooled test metrics describe many historical origin/lead-day forecasts rather than 48 independent months.

Candidates are same-weekday-last-week seasonal naive (weekly pattern repeated across the horizon), additive weekly ETS, XGBoost autoregression on 28-day lags, and a Ridge model with training-only mutual-information feature selection and PCA. Models are selected separately for each horizon using validation MAE.

**In summary:** we tested four different forecasting approaches, a simple "same as last week" guess, a classic statistical smoothing method (ETS), a machine learning model (XGBoost), and a simpler linear model (Ridge), and picked whichever one scored best on a held out validation period, separately for the 1 week and 1 month forecasts.

## 7. Metric and uncertainty meaning

MAE is the average daily miss in tickets. RMSE is also in tickets and penalizes larger misses more. WAPE is total absolute error divided by total actual volume; sMAPE is a symmetric relative-error measure. MAPE is avoided around zero actual counts. The displayed symmetric 90% interval uses a validation-only quantile of absolute residuals. Its measured test coverage is below the nominal 90% for the selected model; calibration is imperfect and not guaranteed to persist.

**In summary:** MAE and RMSE summarize daily forecast errors. Nominal 90% intervals covered 86.55% of test forecasts for selected 7-day XGBoost and 87.71% for primary 30-day ETS. They under-cover and should not be treated as guaranteed ranges.

## 8. Feature design and explainability

Features use the preceding 28 daily counts, 7/28-day rolling means, weekday sin/cos and annual-cycle sin/cos. Mutual-information selection and PCA are fitted on the early training period. The Ridge pipeline repeats fitting within each forecast origin. XGBoost SHAP values are calculated on validation dates from a model fitted only on pre-validation data; the leading contributions are lags 28, 21 and 14.

Interpret primary 30-day ETS through its level, trend and weekly seasonal structure. SHAP explains XGBoost, now selected at 7 days and a challenger at 30 days, not ETS or every recursive multi-step forecast. Correlated lag features can share importance; these are not causal explanations or proof that the patterns drive real-world demand.

**In summary:** XGBoost diagnostics highlight past days influencing validation predictions, mostly 2 to 4 weeks earlier. The separate primary ETS model uses interpretable trend and weekly seasonal components; it needs its own interpretation rather than XGBoost explanations.

## 9. Ethical and fairness interpretation

The source contains masked project/reporting identifiers, not approved protected demographic attributes. Protected-group fairness cannot be assessed. The priority reference comparison is partly defined by priority-specific thresholds, so between-priority attainment differences are not a standalone fairness test. Small project-group results should not be ranked. The daily forecast is one aggregate series, so it cannot reveal whether forecasts under-serve a queue, site or shift. If those approved segments become available, audit signed bias, error and interval coverage and retain human capacity-planner review.

**In summary:** the data does not include anything like age, gender, or location, so we genuinely cannot check for demographic bias, not because we skipped it, but because that information was never collected. We can compare across the project labels that do exist, but that is a stand in for operational fairness, not a real fairness audit.
